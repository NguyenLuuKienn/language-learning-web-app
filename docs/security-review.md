# Security review (2026-10-22)

## Implemented

- Learning content and media APIs require authentication; only language metadata remains anonymous.
- Login and registration have a per-client-IP fixed-window limit; refresh has a separate limit. In Docker, nginx overwrites `X-Forwarded-For`, the API is private to the Compose network, and the API trusts that header only when explicitly configured.
- CORS accepts configured origins only. The Docker frontend proxies `/api` to the API on the same origin.
- Production startup requires a database connection and a JWT signing key of at least 32 bytes. Development generates a temporary JWT key when none is supplied. Demo users are seeded only in Development.
- Existing access tokens fail when an account is disabled, its role changes, or its password changes. JWT validation reads the current account state on each authenticated request.
- New passwords require 15–128 characters. New PBKDF2-HMAC-SHA256 hashes use 600,000 iterations; old hashes remain verifiable. Malformed stored hashes fail closed.
- Uploaded media filenames use an extension derived from the accepted MIME type. API responses send `X-Content-Type-Options: nosniff`.
- Browser authentication now uses HttpOnly access and refresh cookies with SameSite=Strict, Secure outside Development, CSRF header validation for cookie-backed writes, refresh rotation, and logout revocation. The frontend removes legacy tokens from localStorage and restores sessions from cookies.
- Refresh and logout accept only the refresh cookie; the legacy refresh-token JSON body path has been removed. Refresh rotation atomically revokes the old token before issuing a new one, and replay is rejected.
- Auth endpoints return profile data without access or refresh tokens in JSON. Bearer authentication remains accepted for service clients that obtain credentials through a separate trusted process.
- Placement questions are served without answer keys. Learners upload WebM recordings for speaking and submit written answers. Attempts remain pending until an administrator listens to the recording, grades speaking and writing per question, and records feedback. Only a reviewed passing attempt can issue a short-lived user/course-bound proof. Initial target selection and language/level changes require that proof. Administrators can create and edit four-skill placement tests for a course through JSON or the web editor.
- Learner course material, course details, enrollment, lessons, quiz, decks, cards, SRS, progress, vocabulary search, media, CSV and offline sync are scoped to the stored language and level. Public decks without a level tag are hidden from learners. The frontend clears local offline study data after a target change or logout. Uploaded placement recordings can be read only by their owner and administrators. Review actions are recorded in the audit log.
- Placement attempts and recording ownership are persisted in the database. Docker Compose persists media files and Data Protection keys in named volumes.
- Production startup now fails if the database cannot be initialized or persistent Data Protection key storage is not configured. Compose requires database credentials rather than falling back to sample passwords and binds MySQL's published port to localhost. General media uploads check file signatures and the actual byte count, and are rate limited. The API and nginx set framing, MIME sniffing, referrer and browser permission headers; nginx also sets a same-origin content security policy.
- Account registration and profile updates reject unknown time zones. Email addresses are normalized and limited to 254 characters, new passwords require 15–128 characters without control characters, and display names are checked after trimming. Course titles must contain 2–200 visible characters after trimming, and descriptions are limited to 2000 characters. The auth and admin forms mirror these limits. The frontend settings requests now use the actual profile, daily-goal and password endpoints and payloads.
- The unused anonymous WeatherForecast sample endpoint was removed.
- Backend request validation rejects blank or oversized course, unit, lesson, language, vocabulary, deck and card fields, empty required GUIDs, invalid review ratings, empty card batches and unsupported progress states. Course level and domain are checked against the selected language framework and the supported domain list. Vocabulary creation requires an existing lesson in the selected language. Admin status and visibility changes require an explicit boolean, and role changes reject unknown enum values. The service layer also checks normalized account, course, card, vocabulary and progress values so direct service calls cannot persist those invalid values.
- Course material JSON import validates nested unit and lesson identifiers, flashcards, reading content and quizzes, writing instructions, and quiz answers on the backend before saving. An invalid nested field returns 400 even when the request bypasses the frontend. Excel curriculum import is not implemented yet; it must reuse backend material validation before any database write.
- Business and validation errors now include a stable `code` in ProblemDetails. Auth and course-title rules use centralized codes and messages; the frontend maps those codes to English or Vietnamese. Other service errors still use legacy literal messages and should be migrated incrementally without changing their existing status codes.
- Administrators can edit one lesson's vocabulary, listening, speaking, reading, writing, grammar and quiz entries through a dedicated web dialog and `PUT /api/v1/admin/courses/{courseId}/lessons/{lessonId}/material`. Backend validation runs before a single database save; vocabulary and quiz tables are synchronized with the course material. Deleting a quiz question with submitted answers is rejected to preserve history. Placement editing is accessible directly from each course row, scoped to that course's language and level.

## Remaining work, in priority order

1. Decide whether trusted non-browser clients still need Bearer access; browser JSON responses no longer expose tokens. Add an explicit access-token revocation strategy if immediate logout invalidation is required. A previously issued access token remains valid until expiry after logout.
2. Remove or rotate any previously deployed sample JWT key and disable or replace demo accounts already present in a production database. Startup no longer seeds them, but existing records remain.
3. Implement Google sign-in with a configured OAuth client ID. Verify the ID token signature, issuer, audience, and expiration on the server, and link identities by Google's stable `sub` claim. Do not automatically merge an existing password account based only on email. No Google credentials are configured in this repository.
4. The four-skill placement exam now uses human review for speaking and writing. Add a speech transcription/pronunciation provider and calibrated writing assessment only if automated grading is required. Listening still uses browser text-to-speech from `audioScript`, so authored recordings and examination controls remain future work. Proofs expire after 10 minutes but can be reused by the same account and course within that window.
5. Review historical aggregate statistics after a target switch. Current deck, due-card and lesson-progress counts are scoped, while lifetime activity may reflect earlier study targets. Offline study data is cleared on target changes and logout, but existing data from older versions may remain until one of those actions occurs.
6. Signature checks only identify common container headers; they do not establish that media is decodable or safe. Add media decoding/transcoding and malware scanning if arbitrary uploads remain enabled. Configure TLS at the public reverse proxy: the bundled nginx listens on HTTP only. Revisit the nginx content security policy when Google Identity Services is integrated.
7. Provision the first production admin through a controlled one-time process. Startup currently creates `admin@languagelearning.app` when it is absent and `Bootstrap:AdminPassword` is configured; remove this automatic bootstrap path after provisioning.

See [production-readiness.md](production-readiness.md) for the current release gates, including database migration and vocabulary data quality.

## Verification

- Backend: 48 unit tests and 47 integration tests passed. Integration tests cover level-scoped deck/SRS/progress/vocabulary/media access, admin placement editing before and after course material import, individual lesson material editing, recording upload and playback, pending review, proof issuance, course/lesson/quiz access before and after unlocking, account/course/deck/card/admin input validation through the API, settings endpoints, JSON refresh rejection, and refresh-token replay rejection. The legacy bulk curriculum import endpoint was removed because it bypassed course-first material validation. Unit tests cover spoofed media MIME types and mismatched upload lengths.
- Frontend: production build passed; all 10 browser E2E cases reported `ok` on a temporary development database. The runner did not exit cleanly after the last case, so it was stopped after confirming all case results.
- The actual `english_A2_general_import_repaired.json` was imported through the admin API into a temporary SQLite database in the previous verification run. The placement API served 20 questions across four skills without answer keys. That earlier text-only grading flow has been replaced by human review and must be exercised with a real recording before production use.
- Docker Compose and nginx configuration were reviewed statically; Docker daemon was unavailable for a container smoke test.
